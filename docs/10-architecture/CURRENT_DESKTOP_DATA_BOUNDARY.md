## Read topology and invalidation context

`CanonicalShell` renders only the active module. Navigating Today → Bookings → Today unmounts then remounts Today, so the initial Today read runs again. The same pattern can repeat other module initial reads. This is a baseline characteristic, not an instruction to keep all views mounted.

Static request counts for common paths: Today 1 API; Bookings list 1 direct PostgREST read; New Booking options 4 parallel direct reads plus conditional customer searches; populated Customers list/detail 2 API reads; Attendance workspace 1 API and History 1 additional API; Schedule day 2 API and week 7 daily + 1 availability = 8 API; Home Service queue + drivers + selected detail + recommendations up to approximately 4 API reads, fewer when empty; Staff roster 1 + services 1 (conditional rules +1) + applications 1 + schedule-week 2 = **5 minimum, 6 when rules queried** direct reads. These are source-derived logical request counts, not measured traffic or latency.

Existing mutation paths are inventoried only for future invalidation: Today `mutateToday`; Bookings `createBranchBooking`, `cancelBranchBooking`, `rescheduleBranchBooking`; Attendance `mutateAttendanceException`, `updateAttendanceRules`; Schedule `mutateSchedule`; Home Service `mutateHomeService`, `rescheduleHomeServiceBooking`, `cancelHomeServiceBooking`; Staff `updateStaffProfile`, `updateStaffCapabilities` (actor-aware RPC), `adjustStaffSchedule`, `reviewOnboardingRequest`, `updateStaffSystemRole`, `deactivateStaff`. No Stage 14 timing wrapper touches a write. Future cross-module invalidation is specified in [`LOCAL_DATA_CACHE_CONTRACT.md`](LOCAL_DATA_CACHE_CONTRACT.md).
