## State and reconciliation

| Logical state       | Required future UI/authority meaning                                                                                                                                           |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Missing             | No valid snapshot for the authenticated user, branch, dataset and parameters; use authoritative online read or truthful unavailable/error state.                               |
| Cached/stale        | Valid scoped snapshot exists but freshness is unverified; display the source timestamp and stale status, never a fresh/server-verified badge.                                  |
| Refreshing          | Authoritative read is in flight; previously valid cache may remain visible with a refreshing indicator.                                                                        |
| Fresh               | A matching, validated authoritative response completed in the current authenticated context; only then may a snapshot be treated as server-verified.                           |
| Offline-with-cache  | Network unavailable; valid matching snapshot is read-only context with explicit offline/stale label and timestamp.                                                             |
| Error-with-cache    | Network/validation/permission failure; retain a valid matching snapshot as stale context where policy permits, show the error, deny authoritative actions until server checks. |
| Error-without-cache | No safe snapshot; show error/unavailable state, never fabricated empty data.                                                                                                   |

A snapshot restored from disk after restart **always starts cached/stale**, even if recent. It must not silently present itself as freshly server-verified. The UI may render it quickly while beginning the required authoritative reconciliation. No cached record, role, capability, staff status, booking lifecycle, availability or recommendation may authorize a mutation; the existing hosted mutation path must revalidate the actor and current state.

Only a successful authoritative read that passes the current response validator and matches authenticated user/branch scope may replace a cache entry. A **verified authoritative empty response** may replace older data. A failure, malformed response, permission denial, branch mismatch, expired session or network error must not overwrite a valid snapshot with `[]`, `{}`, `null`, zero KPIs or a fake empty state. Network failure keeps matching cache stale. A read model without proven branch isolation is cache-blocked.

## Identity, privacy and lifecycle

Every future key needs authenticated user ID, branch ID, dataset, relevant query parameters/window, and dataset/schema version. Conceptual entry: `userScope`, `branchScope`, `dataset`, `parametersHash`, `schemaVersion`, `storedAt`, `validatedAt`, `payload`. This is not a schema implementation. `dataset=bookings` alone is unsafe on a shared workstation. Never fall back across user or branch. Cache remains inaccessible before authentication and namespace match on launch. Explicit logout must purge or make the user's cached business data inaccessible. Ordinary close may retain a future cache only under these rules.

Never persist raw login password, Supabase password, access/refresh token, service-role key, database password, signing secret, `CRON_SECRET`, or privileged server credential. Cache storage is not an auth vault; session persistence has a separate security contract. Customer, staff, applicant, address and location data are private business data; the future implementation must define protection/retention before writing them to disk.

Unknown schema version or corrupt payload: ignore/discard entry and perform an authoritative refresh. Unavailable local database: use existing hosted online reads. Local write failure after a successful hosted read: keep the validated response usable in current session and report persistence failure truthfully. Cache faults must not make the online CRM unusable.

Future reconciliation is single-flight per key. Concurrent readers can share a refresh; generation/version tracking must prevent an older completion overwriting a newer validated result. Unmount/cancel must not corrupt cache. No part of this concurrency mechanism is implemented in Stage 14. No new worker, polling or Realtime is authorized. If future Realtime is separately approved, an event should mark affected keys stale and trigger controlled reconciliation, not become independent authority.

## Targets and implementation direction

**TARGETS — NOT CURRENT OBSERVATIONS.** On the target Windows front-desk machine: valid scoped cached content should render without waiting for network or a full-screen skeleton; local lookup plus validation P95 ≤ 100 ms; navigation to useful cached content P95 ≤ 250 ms. Reconciliation follows asynchronously. Return to a still-valid cached module should avoid redundant identical blocking reads unless refreshed/invalidated. At most one authoritative refresh per key is active. Actual target hardware may require an evidence-backed revision, never silent adjustment.

Prefer validated read-model/response snapshots first, rather than cloning the hosted relational database. This preserves current validated Desktop read contracts, limits local business-rule divergence, narrows implementation/invalidation/versioning, and eases rollback. A normalized relational projection requires measured need and separate authorization. Stage 14 does not select or install any SQLite library/plugin or define a physical schema.
