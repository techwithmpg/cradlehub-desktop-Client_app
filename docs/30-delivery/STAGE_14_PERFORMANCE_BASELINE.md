## Authenticated measurement procedure for owner review

1. Use an already authorized owner runtime with the exact Stage 14 branch/build. Do not share credentials or record payloads. Start the native app via `pnpm tauri dev` only if the environment permits; identify any process already using port 1420 and never kill an unknown listener. Authenticate normally. Record machine/build/branch, network condition and UTC/local capture time outside business payloads.
2. In development, capture only `[CradlePerf] <fixed-operation> <duration>ms <success|error>` lines or the detached result of `getReadPerformanceSnapshot()` from the renderer console. Clear metrics with `clearReadPerformanceMetrics()` before each scenario. Do not include query terms, IDs, customer/staff names, URLs, tokens or response bodies. A successful timing means service completion, not UI paint or deployed policy validation.
3. Take **at least three samples per core initial-load scenario** when authenticated and observable. Record per operation and end-to-end scenario **sample count, min, median, max**, with the exact observation source (`implementation-agent native observation` or `OWNER-PROVIDED MANUAL RUNTIME EVIDENCE`). If a scenario is data-dependent, state whether queue/list selection existed; do not create production data just to fill a row.
4. Measure Today first load, manual refresh and away/return; Bookings first load, refresh and New Booking options; Customers list, initial selected detail, one search and away/return; Attendance workspace, a History week and away/return; Schedule day, week, another week and return to day; Home Service empty or populated queue, drivers, and selected detail/recommendations where available; Staff initial workspace and refresh, inspecting the four logical child timings. Treat nested `schedule.week` and `schedule.day` samples as overlapping, never additive wall time.
5. Compare console counts with the static matrix, record any mismatch as a finding rather than editing the expected topology without source review. No production mutation is needed for this gate. Keep durations `NOT OBSERVED` until real native, authenticated samples exist.

The future product goals in [`LOCAL_DATA_CACHE_CONTRACT.md`](../10-architecture/LOCAL_DATA_CACHE_CONTRACT.md) are **TARGETS — NOT CURRENT OBSERVATIONS**: local lookup/validation P95 ≤ 100 ms and useful cached navigation P95 ≤ 250 ms on the target Windows front-desk machine. Stage 14 has no cache and no before/after speedup claim.
